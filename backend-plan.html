TMS Backend Architecture Plan

Express API in front of PostgreSQL schemas, triggers, and functions. This document records the design and current implementation direction.

1. Overview

The backend is designed as a thin Express API. Core business rules, integrity checks, and audit logging reside directly inside the database through constraints, triggers, and PL/pgSQL functions. The API authenticates callers, enforces role and ownership constraints, executes database queries, and maps PostgreSQL error codes to standardized HTTP responses.

The database consists of six schemas:

  • accounts: Handles user credentials, profiles, and password resets (OTP stored on user rows).
  • fleet: Manages vehicles, maintenance records, driver profiles, and fuel logs.
  • operations: Holds route templates, scheduled trips, driver incident logs, and bookings.
  • billing: Processes invoices and incoming payment records.
  • monitoring: Stores notification alerts and security audit trails.
  • extensions: Houses extension functions such as pgcrypto (for crypt and gen_salt).

What the Database Handles for the API

  • operations.validate_trip_assignment: Rejects trip creation if the vehicle is in maintenance, if insurance or vehicle license is expired, or if the driver is off duty, unverified, or has an expired license (raised as exception code P0001).
  • operations.set_trip_times and operations.sync_trip_status: Fills actual_start / actual_end automatically and keeps vehicle and driver statuses synchronized with trip status transitions.
  • billing.update_invoice_after_payment: Automatically transitions an invoice status to paid when completed payments satisfy the total invoice amount.
  • monitoring.log_audit: Records all INSERT, UPDATE, and DELETE operations across key tables into monitoring.audit_logs.

What the database does NOT do: No database trigger creates an invoice from a booking (bookings hold no price column), and invoice status is limited to unpaid, paid, or overdue. Invoices are created separately by an administrator via the API, who provides the invoice total and invoice number.

2. Core Infrastructure

backend/db.js: Connection Pool and Transaction Helper

Uses connection parameters from backend/.env (DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD). The transaction helper executes sequential queries inside a single database transaction and sets the user context for the audit logging trigger.

backend/db.js PostgreSQL Connection Pool & Transaction Wrapper 
const { Pool } = require('pg');

const pool = new Pool({
  host: process.env.DB_HOST,
  port: parseInt(process.env.DB_PORT || '5432', 10),
  database: process.env.DB_NAME,
  user: process.env.DB_USER,
  password: process.env.DB_PASSWORD,
  max: 20,
  idleTimeoutMillis: 30000,
});

pool.on('error', (err) => console.error('Idle pool client error', err));

/**
 * Execute multiple statements sequentially in ONE database transaction.
 * set_config(..., true) is local to the transaction block, setting context
 * for monitoring.log_audit() to record the acting user ID.
 */
async function transaction(userId, callback) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    if (userId) {
      await client.query("SELECT set_config('app.current_user_id', $1, true)", [userId]);
    }
    const result = await callback(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}

module.exports = { pool, query: (t, p) => pool.query(t, p), transaction };

Every write query runs through transaction(req.user.id, ...). Read-only queries can execute directly via pool.query.

backend/utils/dbError.js: Database Error Translation

Translates errors based strictly on PostgreSQL error codes rather than parsing message text, ensuring internal database structures are never leaked in error responses. Exported as module.exports = handleDbError.

backend/utils/dbError.js Error Translation Utility 
function handleDbError(err, res) {
  console.error('Database error caught:', err);

  // User exceptions raised by custom functions & triggers (e.g. RAISE EXCEPTION)
  if (err.code === 'P0001') return res.status(400).json({ error: err.message });
  // Not found exceptions raised by stored functions (e.g. accounts.update_user_profile)
  if (err.code === 'P0002') return res.status(404).json({ error: err.message });

  switch (err.code) {
    case '23505': return res.status(409).json({ error: 'Record already exists.' });
    case '23503':
      if (err.detail && err.detail.includes('is still referenced'))
        return res.status(409).json({ error: 'Record is referenced by other items and cannot be removed.' });
      return res.status(400).json({ error: 'Referenced dependency does not exist.' });
    case '23514': return res.status(400).json({ error: 'Validation constraint failed.' });
    case '23502': return res.status(400).json({ error: 'A required field is missing.' });
    case '22P02':
    case '22007': return res.status(400).json({ error: 'Invalid ID format or date value.' });
  }
  return res.status(500).json({ error: 'Internal server error.' });
}

module.exports = handleDbError;

backend/middleware/auth.js: Authentication & Authorizations

  • authenticate: Parses the Authorization: Bearer <token> header, verifies signature using JWT_SECRET, and extracts req.user = { id, role }. Token expires per JWT_EXPIRES_IN.
  • Checks user status (is_active) on each request via a fast primary key query so deactivated user tokens are immediately invalidated.
  • requireRole(...roles): Rejects unauthorized roles with HTTP 403 Forbidden.
  • Driver ID Lookup: Since JWTs carry user IDs, driver routes look up driver profiles via SELECT id FROM fleet.drivers WHERE user_id = $1.

3. Authentication and Password Reset

User Registration

POST /api/auth/register invokes accounts.register_user(...) and creates customer accounts only. Administrators create driver accounts through the protected driver-registration endpoint.

Password Handling & Hashing

The Express API submits plain passwords to register_user and complete_password_reset, where the database handles hashing using extensions.crypt (bcrypt, cost factor 10, hashes starting with $2a$10$). TLS connections and disabled statement logging protect plain-text passwords in transit.

Login Verification

  1. Query user record using accounts.get_user_for_login(identifier). Returns no rows for unknown or deactivated users.
  2. Verify password via Node's bcrypt.compare(password, row.password_hash) thread pool handler.
  3. Return generic 401 ("Invalid username or password") on missing user or invalid password to prevent account enumeration.
  4. On successful validation, return signed JWT payload { id, role }. Never expose password_hash or otp in responses.

Password Reset Flow (OTP)

  1. Request: Generate a 6-digit numeric OTP using crypto.randomInt(100000, 1000000) and invoke accounts.request_password_reset(email, otp). Always respond with a generic success message. Print OTP to console in development environment; dispatch via email/SMS service in production proposed. Codes expire in 10 minutes.
  2. Verification: Client sends email, OTP, and new password. Query accounts.get_active_reset(email) to fetch the corresponding user ID. Return HTTP 400 if no active reset request is found.
  3. Completion: Invoke accounts.complete_password_reset(user_id, otp, new_password) to update the password.
  4. Failure Logging: If complete_password_reset throws exception code P0001, execute accounts.record_failed_reset_attempt(user_id) inside a separate pool.query outside the failed transaction to increment the attempt counter without being rolled back.

5. Ownership and Security Rules

Customer Joins for Scoped Record Access

Since billing.invoices and billing.payments lack direct user_id foreign keys, customer queries enforce access ownership through relationship joins to operations.bookings:

Customer Ownership Query Joins SQL Filtering Examples 
-- Bookings query
SELECT * FROM operations.bookings
WHERE user_id = $1;

-- Invoices query
SELECT i.* FROM billing.invoices i
JOIN operations.bookings b ON b.id = i.booking_id
WHERE b.user_id = $1;

-- Payments query
SELECT p.* FROM billing.payments p
JOIN billing.invoices i ON i.id = p.invoice_id
JOIN operations.bookings b ON b.id = i.booking_id
WHERE b.user_id = $1;

Driver Data Access Rules

Driver endpoints retrieve the driver ID using SELECT id FROM fleet.drivers WHERE user_id = req.user.id and restrict queries for trips, fuel entries, and incidents to that specific driver ID.

Security Protections

  • Never Trust Payload IDs: User profile updates rely exclusively on req.user.id extracted from the JWT token. Customers cannot alter booking or payment statuses beyond pending.
  • Rate Limiting: Enforce rate limiting via express-rate-limit (20 attempts / 15 mins for /api/auth/login; 3 attempts / hour for /api/auth/request-reset).
  • Deactivated Accounts: User active status (is_active) is checked on every authenticated request to immediately block deactivated account tokens.
  • Secret Management: Environment configurations and passwords are stored in .env and excluded from source control.

6. Audit Trail Integration

All database write operations execute inside the pool helper transaction(req.user.id, ...), setting the session context via SELECT set_config('app.current_user_id', $1, true). The database trigger monitoring.log_audit reads this configuration setting to log the responsible actor in monitoring.audit_logs. Unauthenticated writes record a NULL user ID.
